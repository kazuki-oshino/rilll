# agent-learnings-consolidator

利用先プロジェクトの `docs_dev/playbook/` にある近接したトピックを集約する。
学習ワークフローは既存の知見へ追記するため、同じ対象について小さなトピックが増えることがある。
このスキルは明示的な依頼で実行し、集約案を確認してから適用する。

## 保存形式と変更範囲

カテゴリは `failure-recovery`、`antipattern`、`success-procedure`、`tool-pattern` の4種類。
各カテゴリは `<category>.md` という1ファイルに保存され、`## <topic>` から次の `## ` またはファイル末尾までが1セクションとなる。
カテゴリファイルと `index.md` にYAML frontmatterはない。

```markdown
# tool-pattern

ツールやAPIの使い方をまとめる。

## go-test
**適用条件:** Goのテストを追加または修正するとき
**summary:** Goテストの実行と環境分離

- テストの一時ファイルは t.TempDir() 配下に作成する。
```

変更対象は集約するカテゴリファイルと `index.md` のみ。
カテゴリファイル自体の削除、トピックごとのファイル作成、Gitのステージ操作やコミットは行わない。
このスキルはファイル上の知見を整理するものであり、SQLiteに保存された過去の実行記録は変更しない。

守る条件:

- 集約は同じカテゴリ内に限る。
- 既存の箇条書きは原文と出現数を保持する。重複していても削除、要約、言い換えをしない。
- 集約後は1トピックにつき5件以下とする。既存の集約先にある箇条書きも数に含める。
- カテゴリの冒頭説明と、集約対象外のセクションはそのまま保持する。
- トピック名は `^[a-z][a-z0-9-]*$` に従い、同じカテゴリ内で一意とする。
- 適用条件とsummaryは、それぞれ空でない100文字以内の1行とする。

## 1. 現在のトピックを読む

1. 4種類のカテゴリファイルと `index.md` の有無を確認し、存在するものを読む。カテゴリファイルがなければ変更せず終了する。
2. 各カテゴリの先頭から最初の `## ` までを冒頭説明として保持し、以降をセクション単位で読む。
3. 各セクションのトピック名、`**適用条件:**`、`**summary:**`、`- ` で始まる箇条書きを抽出する。カテゴリ名はファイル名から取得する。
4. 元のファイル内容を比較用に保持する。重複した見出し、欠落したメタデータ、複数行の箇条書きなど、上記の形式で扱えない内容があれば、そのカテゴリを集約対象から外して理由を報告する。認識できない行を捨てて書き直さない。

`index.md` は一覧用の派生データであり、カテゴリファイルを正本とする。
旧形式のカテゴリサブディレクトリやfrontmatter付きトピックファイルは、このスキルでは移行しない。

## 2. 集約案を作る

同じ対象や場面を扱い、適用条件が両立するトピックを候補にする。
たとえばGoテストのキャッシュと環境分離は同じトピックにまとめられるが、無関係な操作を「ツールの注意点」のような広すぎる名前でまとめない。

各案には次を含める:

- `category`、集約元の `from[]`、集約先の `into`
- 集約理由と、集約後の箇条書き数
- 集約後の適用条件とsummary
- カテゴリファイルと索引の変更差分

`from[]` は重複のない既存トピック名とし、`into` を含めない。
新規の集約先には2つ以上の集約元が必要で、既存の集約先には1つ以上の集約元が必要となる。
既存の集約先を使う場合、その適用条件とsummaryを保持し、集約元の内容もその範囲に収まる案だけを採用する。
新規の集約先には、全ての集約元に共通する対象を表す名前とメタデータを提案する。
1つのトピックが複数の案に登場する集約や、ある案の出力を別の案へ渡す連鎖は避ける。

同じカテゴリ内で5件に収まる案がなければ、集約候補なしとして終了する。
候補の判断はスキルを実行するエージェントが行い、追加のエージェントは起動しない。

## 3. 差分を確認する

実際に適用する差分を提示し、ユーザーが選んだ案だけを適用する。
既に具体的な集約案への適用許可がある場合は、その範囲内で進める。
確認が必要な場合は、利用環境の質問ツールまたは会話で、全案の適用、一部の選択、見送りを選べるようにする。

## 4. セクションと索引を更新する

1. 書き込み前に対象ファイルを再読し、差分を作った時点から変更されていないことを確認する。変更があれば上書きせず、最新の内容で案を作り直す。学習ワークフローが並行して書き込んでいる場合は適用を止める。
2. カテゴリごとに、許可された案を反映したファイル全体をメモリ上または一時ファイルに作る。
   - 既存の集約先は同じ位置とメタデータを保持し、その箇条書きの後へ `from[]` 順に原文を追加する。
   - 新規の集約先は最初の集約元の位置に作り、提案したメタデータと `from[]` 順の箇条書きを置く。
   - 集約元のセクションを取り除く。対象外のセクションと冒頭説明は元の内容を保持する。
3. 書き込む前に、全箇条書きの原文と出現数がカテゴリ内で一致すること、対象外の内容が一致すること、集約先が5件以下であること、見出しが一意であることを確認する。
4. カテゴリファイルは一時ファイルへの書き込み後に置き換えるなど、途中の内容を残さない方法で保存する。集約元の削除と集約先の更新を別々のファイル操作にしない。
5. 保存後の4カテゴリを再読し、`index.md` を更新する。カテゴリの順序は `failure-recovery` → `antipattern` → `success-procedure` → `tool-pattern` とする。
   - 既存の索引のタイトル、案内文、カテゴリごとの説明は保持する。
   - カテゴリ内のトピック順に `- [topic](./category.md#topic) — summary` を出力する。
   - 集約元のリンクを残さず、集約先のリンクとsummaryを反映する。
   - 索引がない場合は `# Playbook Index`、適用条件を確認してから利用する旨の案内、4カテゴリの見出しと一覧を作成する。
   - 存在しないカテゴリは空の一覧として扱う。読み取りに失敗したカテゴリがあれば、不完全な索引で上書きせず停止する。
6. 保存したファイルを再読し、箇条書きの保持、集約元見出しの除去、集約先の件数、索引のリンク先を確認する。変更したファイルと集約内容を報告する。

カテゴリファイルと索引の更新は複数ファイルにまたがるため、一括での原子的な更新ではない。
途中で失敗した場合は後続操作を止め、更新済みと未更新のファイルを報告する。
索引だけが更新できなかった場合は、保存済みのカテゴリファイルから索引を再生成する。
カテゴリを無条件に巻き戻したり、Git操作で復旧したりしない。
